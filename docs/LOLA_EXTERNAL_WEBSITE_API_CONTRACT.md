# LOLA External Website API Contract

This contract is for wiring the existing standalone HTML/CSS/JavaScript LOLA marketing website into the LOLA Admin backend. Do not rebuild the public website in this repository, do not redesign the static site, and do not change public API response shapes unless a backend bug is found.

## Public API Base

Local API base:

```text
http://localhost:4000
```

External website requests should append the route path to the configured backend origin:

```js
const LOLA_API_BASE = window.LOLA_API_BASE || "http://localhost:4000";
const url = `${LOLA_API_BASE}/api/public/site`;
```

Production is environment-driven. Use the deployed LOLA Admin API origin, for example `https://<admin-api-host>`, but do not hardcode a final public domain until one is actually configured.

## Marketing CMS Endpoints

- `GET /api/public/site`
- `GET /api/public/homepage`
- `GET /api/public/hero-slides`
- `GET /api/public/packages`
- `GET /api/public/experiences`
- `GET /api/public/events`
- `GET /api/public/gallery`
- `GET /api/public/gallery?category=WEDDINGS`
- `GET /api/public/gallery?featured=true`
- `GET /api/public/testimonials`
- `GET /api/public/faqs`
- `GET /api/public/media/:id`
- `POST /api/public/inquiries`

The marketing website needs no API key, admin token, client secret, or signed customer token for these marketing endpoints.

## Transaction Customer Endpoints

These are public customer workflow endpoints, not marketing CMS endpoints:

- `GET /api/public/delivery/:token`
- `GET /api/public/proposals/:token`
- `GET /api/public/proposals/:token/preview`
- `GET /api/public/proposals/:token/pdf`
- `POST /api/public/proposals/:token/accept`
- `POST /api/public/proposals/:token/decline`
- `GET /api/public/invoices/:token`
- `POST /api/public/invoices/:token/payment-session`
- `GET /api/public/invoices/:token/pdf`

The external marketing site should link to these only when it already has a secure token generated by LOLA Admin.

### GET /api/public/media/:id

Success returns the raw file bytes, not JSON. Public media JSON references are relative URLs like `/api/public/media/<uuid>`, so the external website must prefix the API base when fetching from another origin:

```js
function apiAsset(path) {
  return path && path.startsWith("/api/") ? `${LOLA_API_BASE}${path}` : path;
}
```

Missing media example:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Media not found",
    "requestId": 77
  }
}
```

Media is streamed through the API storage adapter. It is not redirect-based. Response `Content-Type` is the stored `mime_type`. Upload validation currently allows `image/jpeg`, `image/png`, `image/webp`, and `application/pdf`; public media delivery only requires the record to be `visibility='PUBLIC'` and `permission_state='APPROVED'`.

## Visibility Rules

Public content is filtered by the backend:

- Hero slides: `is_active=true`, `status='PUBLISHED'`, within `publish_start`/`publish_end` when present.
- Packages: `deleted_at IS NULL`, `active=true`, `show_on_website=true`.
- Experiences: `deleted_at IS NULL`, `active=true`, `show_on_website=true`.
- Event types: `deleted_at IS NULL`, `show_on_website=true`, `status='PUBLISHED'`.
- Gallery: `deleted_at IS NULL`, `status='PUBLISHED'`, joined media must be public and approved.
- Testimonials: `deleted_at IS NULL`, `status='PUBLISHED'`.
- FAQs: `deleted_at IS NULL`, `status='PUBLISHED'`.
- Media: `deleted_at IS NULL`, `visibility='PUBLIC'`, `permission_state='APPROVED'`.

## Inquiry Request Contract

`POST /api/public/inquiries` accepts JSON only.

Required fields:

- `firstName`: string, trimmed, min 1, max 80
- `lastName`: string, trimmed, min 1, max 80
- `email`: string, trimmed, valid email, lowercase, max 160
- `phone`: string, trimmed, min 7, max 40
- `eventDate`: string in `YYYY-MM-DD`
- `eventType`: string, trimmed, min 2, max 80
- `city`: string, trimmed, min 1, max 100
- `state`: string, trimmed, min 2, max 40

Optional fields:

- `eventStartTime`: string matching `HH:MM`
- `eventEndTime`: string matching `HH:MM`
- `guestCount`: positive integer, coerced from numeric string
- `venueName`: string, trimmed, max 160
- `venueAddress`: string, trimmed, max 240
- `zip`: string, trimmed, min 3, max 20
- `preferredExperienceId`: UUID
- `preferredPackageId`: UUID
- `referralSource`: string, trimmed, max 120
- `message`: string, trimmed, max 3000
- `utm_source`: string, trimmed, max 120
- `utm_medium`: string, trimmed, max 120
- `utm_campaign`: string, trimmed, max 160
- `utm_content`: string, trimmed, max 160
- `utm_term`: string, trimmed, max 160
- `landing_page_url`: string, trimmed, max 500
- `referrer_url`: string, trimmed, max 500
- `marketing_email_opt_in`: boolean
- `website`: string, max 0; honeypot, must be empty or omitted

Not supported by this public schema: `first_name`, `last_name`, `name`, `full_name`, `preferred_contact_method`, `preferred_experience`, `preferred_package`, `estimated_budget`, `lead_source`, `referrer`, or `landing_url`. The backend forces `provider: "WEBSITE"` and `lead_source: "WEBSITE"` during ingestion. Do not send a secret source field.

Static website form mapping:

- `name` should be split into `firstName` and `lastName`, or the HTML should use separate inputs.
- `date` maps to `eventDate`.
- `start_time` maps to `eventStartTime`.
- `event_type` maps to `eventType`.
- `guest_count` maps to `guestCount`.
- `venue` maps to `venueName`.
- `location` should be replaced with separate `city` and `state`, or parsed carefully before submission.
- `experience` maps to `preferredExperienceId` only if the select value is a real UUID from `/api/public/experiences`; otherwise omit it.
- `package` maps to `preferredPackageId` only if the select value is a real UUID from `/api/public/packages`; otherwise omit it.
- `referral` maps to `referralSource`.
- `message` maps to `message`.

Success response, HTTP `201`:

```json
{
  "message": "Thank you. Your inquiry was received and the LOLA team will be in touch soon.",
  "inquiryStatus": "CREATED_LEAD"
}
```

Duplicate behavior: the API does not reject duplicate email or phone submissions. It returns `201` and sets `inquiryStatus` to `POSSIBLE_DUPLICATE` when matching existing lead identity is found. Exact replay detection is based on provider plus generated `external_lead_id`; ordinary website form resubmissions may create a new lead marked possible duplicate.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please check the highlighted fields.",
    "details": {
      "formErrors": [],
```

## CORS

Global CORS allows requests when the origin is omitted, equals `CLIENT_ORIGIN`, or is included in `PUBLIC_INQUIRY_ALLOWED_ORIGINS`. `credentials` is currently `true`.

Inquiry POST has an additional explicit origin gate: if the browser sends an `Origin` header, that origin must be listed in `PUBLIC_INQUIRY_ALLOWED_ORIGINS`, otherwise the API returns `403 CORS_REJECTED`.

Set production env like this, replacing the value with the real deployed static site origin:

```text
CLIENT_ORIGIN=https://<admin-frontend-host>
PUBLIC_INQUIRY_ALLOWED_ORIGINS=https://<public-marketing-site-host>
```

Multiple public origins are comma-separated. Do not use wildcard unless the backend security model is intentionally changed.

## Rate Limit

The whole backend has a global rate limit:

- `RATE_LIMIT_WINDOW_MS`, default `900000` ms
- `RATE_LIMIT_MAX`, default `120`

The public router also has a public-specific limiter:

- `windowMs`: `RATE_LIMIT_WINDOW_MS`, default `900000` ms
- `limit`: hardcoded `20`

Rate-limit responses come from `express-rate-limit`; expect HTTP `429` with standard `RateLimit-*` headers.

## Cache Behavior

Public CMS JSON routes set:

```text
Cache-Control: public, max-age=60, stale-while-revalidate=300
```

Public media sets:

```text
Cache-Control: public, max-age=86400
```

No custom ETag handling is implemented in these routes. The external site can refetch CMS data every page load or keep a short client cache around one minute. Freshly published admin content can take up to the client/CDN cache window to appear.

## Public Error Behavior

- CMS/database unavailable: HTTP `500`, `{ "error": { "code": "INTERNAL_ERROR", "message": "Something went wrong. Please try again.", "requestId": "..." } }`.
- Media missing/not public/not approved: HTTP `404`, `NOT_FOUND`.
- Invalid gallery category: HTTP `200`, empty `data` array if no items match.
- Bad inquiry payload: HTTP `400`, `VALIDATION_ERROR`.
- Disallowed inquiry origin: HTTP `403`, `CORS_REJECTED`.
- Honeypot filled: HTTP `400`, `SPAM_DETECTED`.
- Rate limited: HTTP `429`.

Internal stack traces are not exposed by the error handler.

## Logo and Brand Media

The public API returns default logo paths under `defaults.logo`, but those `/brand/...` paths are not delivered by `/api/public/media/:id`. The external HTML website should ship the approved local vertical/stacked LOLA logo asset and use it as the default header logo. Do not switch to the horizontal logo for the public website unless a very narrow responsive layout truly requires the approved compact fallback.

Document/customer flows should continue using the branded document templates already generated by LOLA Admin. Email headers may use the horizontal logo where compact space requires it.

## Integration Blockers

No blocker prevents the external HTML/CSS/JS website from reading CMS data or posting inquiries.

Current limitations to account for during wiring:

- Public package records do not expose image, slug, CTA, or feature-list fields.
- Public homepage route does not expose dedicated section fields for every static website section; use keyed `content`, `/site`, or static fallback copy.
- Current seed data has no public event types, gallery items, testimonials, or FAQs.
- Public API image URLs are relative; cross-origin static sites must prefix `LOLA_API_BASE`.
- Public brand logo defaults point to `/brand/...` paths; ship the approved vertical logo locally unless CMS intentionally exposes public media for brand assets.
