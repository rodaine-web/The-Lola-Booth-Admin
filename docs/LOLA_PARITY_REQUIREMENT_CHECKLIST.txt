# THE LOLA BOOTH ADMIN
## BoothBook Parity + Event Planning + Creative Production + Production Readiness Sprint

You are working on the existing **The LOLA Booth Admin** application.

This is an established application with substantial frontend, backend, database, payment, CRM, event operations, communications, automation, CMS and field-operations functionality already implemented.

## THIS IS NOT A REBUILD.

## THIS IS NOT A SAAS CONVERSION.

The immediate objective is to make the existing application an excellent, reliable, production-ready operating platform for **The LOLA Booth**.

The product must successfully run The LOLA Booth in live production before any future SaaS conversion is considered.

- SaaS signup

**The LOLA Booth.**

# 4. REUSE BEFORE BUILDING

This rule is extremely important.

Before creating:

- a new database table
- a new route
- a new service
- a new component
- a new notification system
- a new file-storage mechanism
- a new automation mechanism
- a new token mechanism

search the existing application for functionality that already solves all or part of the problem.

Prefer extending existing architecture.

For example:

Event Planning should reuse existing:

- Events
- Clients
- Communications
- Files/storage
- Public tokens
- Automations
- Notifications
- Readiness
- Audit logs

where appropriate.

Do not create parallel systems unnecessarily.

---

# 5. PROTECT WORKING FUNCTIONALITY

Do NOT:

- rewrite the backend unnecessarily
- replace authentication
- remove working APIs
- rename APIs without good reason
- remove existing tests
- bypass RBAC
- weaken file security
- break public website APIs
- replace payment abstractions unnecessarily
- destroy existing data
- hardcode production data

Database changes require migrations.

Important actions require audit history.

Maintain backward compatibility wherever practical.
